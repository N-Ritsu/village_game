# 次のプロジェクトへ引き継ぐ注意点(ふるさと百代記の開発から)

2026-10-25〜11-05 の開発で困ったこと、方針を変えたことから、別のプロジェクトでも役立つものをまとめた。
各項目は「何が起きたか」と「次はどうするか」の順。

---

## 1. 進め方・役割分担

### 1-1. 「書けない」と思い込まず、まず書いてみる
- **起きたこと**: 課金の処理(Edge Functions)を書こうとして、作業環境の安全チェックに一度止められた。それを「私には書けない」と伝えて、手順の説明を何度も繰り返してしまった。後でもう一度書いたら、止められずに書けた。
- **次は**: 止められたら、何が止められたか(書き込みか、実行か)をそのまま伝える。頼まれたら、もう一度試す。説明を繰り返さない。

### 1-2. 本番に関わるコマンドはユーザーが実行する
- **起きたこと**: 次のコマンドは、作業環境の安全チェックで止められた。
  - `supabase secrets set`(秘密の鍵の登録)
  - `supabase functions deploy`(処理の配置)
  - `npm run deploy`(公開)
- **次は**: 本番への反映と鍵の登録は、最初からユーザーの作業として計画する。私は「実行するコマンド」と「実行後に確かめること」だけを伝える。安全チェックを回避しようとしない。

### 1-3. ユーザーがコードを書く前提にしない
- **起きたこと**: 課金の処理を「ユーザーが別のゲーム(policy_simulator)を参考に書く」計画にしたが、難しくて止まった。手作業の決済リンクに切り替えたが、結局は自動にしたくなり、私が書いた。2回回り道をした。
- **次は**: コードは私が書く前提で計画する。ユーザーに頼むのは、アカウント作成・管理画面の設定・本番への反映だけにする。

### 1-4. 記録の残し方
- `docs/history/日付.md` に、毎回「依頼・やったこと・確かめたこと・未確認のこと・ユーザーの作業」を書く。会話が切れても、次の会話で続きから再開できた。
- コードは GitHub に送らず、履歴の文書だけを送る運用にした(`.gitignore` で `docs/` 以外を除外)。

## 2. 構成の選び方(公開・ログイン・保存)

### 2-1. ログインは自前で作らず、既製のサービスに任せる
- **起きたこと**: 最初は Cloudflare Workers + D1 で、登録・ログイン・セーブ・課金を自前で作ろうとして、途中で止まった。Supabase(Google ログイン)に切り替えたら、公開まで進んだ。
- **次は**: ログインと、ユーザーごとのデータは Supabase のような既製のサービスに任せる。画面は静的ファイルとして、Cloudflare などから配信するだけにする。

### 2-2. 無料プランの落とし穴を先に調べる
- Render の無料プランは、使われないと止まり、止まるたびに SQLite のファイルが消える。アカウントが消えてしまうので使えない。
- PythonAnywhere の無料プランは縮小された。
- Cloudflare D1 の無料枠は、1日の書き込み(約10万行)が先に尽きる。1年ごとの自動保存では、50〜100人ほどが限界だった。
- Streamlit は、ボタンのたびにサーバーで全体を動かし直す。ゲームのように素早く反応する画面には向かない。
- **次は**: 計算はブラウザでする。サーバーへの書き込みは「セーブを押したとき」のように回数を絞る。

### 2-3. 端末どうしのセーブの比べ方は、日時でなく番号で
- 日時で比べると、2つ困る。
  - 端末の時計のずれで、古いほうを新しいと判定することがある。
  - 「PCでセーブせずに遊ぶ → スマホでセーブ → PCを開く」と、PCの未セーブ分が黙って捨てられる。
- **次は**: サーバーがセーブ番号を付ける。端末には「どの番号を元にしたか」と「そのあと進めたか」を残す。両方で進めていたら、ユーザーに選ばせる。日時は表示にだけ使う。

### 2-4. 記録が消える選択の前には、必ず確認の画面を出す
- 「ゲストの記録でセーブする」「アカウントのセーブを読み込む」などは、選ばなかった方の記録が消える。小さな注意書きでは足りず、ユーザーに指摘された。
- **次は**: 確認の画面に、何が消えるか(日時つき)と「元に戻せません」を出す。「やめて戻る」で選ぶ画面に戻れるようにする。

### 2-5. ゲームの名前を変えても、保存のキーは変えない
- localStorage のキーを変えると、それまでの記録が読めなくなる。表示名だけを変える。

## 3. 課金(Stripe)

### 3-1. 最終的にうまくいった形
- 決済ページは、サーバーの処理(Edge Function `create-checkout`)が、その場で商品名と値段を渡して作る。
- 支払いの確認は、Webhook を使わず、支払いページから戻ったときとログインしたときに、処理(`confirm-checkout`)が Stripe に問い合わせる。
- 購入の記録は `pending → paid / expired` の状態を持つ。確認では、本人の支払い待ちの行だけを更新し、更新できた行だけを数える(二重に足さない)。
- 決済には `metadata.game` と `client_reference_id`(本人のID)を付けて、確認のときに照らし合わせる。
- 「何を買えるか」の上限は、セーブデータの中でなく、サーバーの購入記録から決める(ブラウザ側の記録は書き換えられるため)。

### 3-2. 回り道したこと
- 決済リンク(Payment Links)にして、世帯枠の付与を手作業にした。ところが「すぐ増えない」とユーザーが不満に感じ、結局は自動にした。
- **次は**: 最初から自動の形(3-1)で作る。決済リンクは使わない。

### 3-3. Stripe のアカウントと鍵
- 2つのゲームで、1つのアカウントを共有した。見分け方は次のとおり。
  - 商品名をゲーム名から始める。
  - `metadata.game` を付ける。
  - 明細書表記の接尾辞を付ける。
  - 鍵はゲームごとに制限付きキーを作る(漏れたら片方だけ止められる)。
- 決済ページに出る事業者名とサポート連絡先はアカウントに1つなので、両方に共通する名前にする。
- 本番の決済リンクは URL に `test_` が付かない。テスト用カードで試すときは、サンドボックスで作る。
- Stripe の「ビジネスウェブサイト」が別のゲームだけになっていて、入金が一時停止された。問い合わせたら解除された。**次は**: 事業内容の説明に、売るものをすべて書いておく。

### 3-4. 本番で購入できなかった(500)
- **原因**: 本番の Supabase は、新しく作った表に、API 用の役割の権限を自動では付けない設定だった(作成画面のおすすめ設定)。購入の処理が直接読み書きする表だけ、`service_role` の権限がなかった。手元の Supabase ではすべて付いていたので、手元のテストでは気づけなかった。
- **次は**: マイグレーションに、表ごとの `grant` を必ず書く(`anon` / `authenticated` / `service_role` のそれぞれ)。「オンでもオフでも同じに動く」定義にする。
- **調べにくかった理由**: 画面がエラーの理由を捨てて、いつも同じ文を出していた。**次は**: 失敗したときは、番号と、どの段階で失敗したかを画面と処理の記録に残す。

### 3-5. 手元と本番の違い
- 手元の Supabase では、事前確認(OPTIONS)と CORS の見出しを、処理の手前の受付(Kong)が付け直す。本番では処理の答えがそのまま届く。処理側でも CORS に答える。
- 手元の Supabase には Google ログインの設定がないので、手元の確認はメールでログインする(開発用。本番では出さない)。
- `localhost` と `127.0.0.1` は、別の戻り先として扱われた。両方を受け付ける。

## 4. 公開の手続き(Cloudflare・Google・規約)

- Cloudflare の workers.dev のサブドメインは、アカウント全体で1つ。今後のゲームにも共通で付くので、ゲーム名ではなく運営者の名前(`nrwebgame`)にした。登録してから開けるまで約80秒かかった。
- **広告(AdSense)を付けるなら、最初から `○○.pages.dev`(Cloudflare Pages)か独自ドメインで公開する。** `workers.dev` と `pages.dev` は「.com」と同じ扱いの一覧(公開サフィックス一覧)に載っている。AdSense は `ゲーム名.nrwebgame.workers.dev` ではなく大もとの `nrwebgame.workers.dev` を求めるが、そこは何も返さない(Workers はゲーム名の付いたアドレスにしか置けない)ので、持ち主の確認が通らない。`ゲーム名.pages.dev` なら、それ自体が大もとになる。あとから移すと、アドレスごとに分かれているブラウザの記録(ゲストのセーブ)の引っ越しまで作る必要があった。
- Google の OAuth 同意画面は「アプリを公開」を押すまで、テストユーザーしかログインできない。公開するとき、ブランディング(アプリ名・サポートのメール・連絡先)を求められる。ロゴを入れると審査が要るので空にした。
- Supabase のログインの戻り先(Site URL・Redirect URLs)は、公開URLが決まってから登録し直す。
- 規約まわり:
  - 問い合わせ先に、専用の Gmail を作った。`+` 付きのアドレスはメインのアドレスが分かるので避ける。
  - 特定商取引法の表記の「請求があれば開示」は、実際に請求が来たら遅れずに開示する義務がある。
  - 「提供時期」は、課金の方式(手作業か自動か)に合わせて直す。
- セキュリティの見出し(CSP)は、読み込み先を自分自身と Supabase だけにした。外のファイルを読む機能を足すときは、ここも直す。

## 6. ゲームの仕組み(数値の作り)

- **買ってすぐ売ると儲かる穴**: 買うときは割引の値段で払うのに、価値は元値で記録していた。割引が15%を超えると、売るだけで儲かった。
  - **次は**: 価値は実際に払った値段から始める。「買う → すぐ売る」で必ず損をすることをテストに入れる。
- **値上がりが複利になっていた**: 前年の値段に率をかけていたので、指数関数的に伸びた。
  - **次は**: 「元値の何%か」「前年の何%か」を最初に決めて、テストで確かめる。
- **乱数は状態の中に持たせる**: セーブとロードのあとでも同じ展開になり、テストで再現できた。PV でも、毎回同じ村を作れた。
- **隠しパラメータは保存せず、人物の seed から計算する**: あとから職業を足しても、すでにいる人物の向き不向きが決まる。
- **データ・仕組み・画面を分ける**(`data.js` / `engine.js` / `ui.js`): 職業を、データに1項目足すだけで増やせた。テストも、仕組みだけを動かして書けた。

## 7. 画面の作り

- **窓(モーダル)が別の窓を上書きした**:
  - 遊び方の窓が、「どちらのセーブで続けるか」の窓を上書きして、選べなくなった。
  - セーブの衝突の窓が出たあと、縁談の窓が出し直されなかった。
  - **次は**: 窓を開く前に、ほかの窓が出ていないかを見る。窓を閉じたら、決めることが残っていないかを見て出し直す。
- **重なり順の不具合**: 位置を持つ要素(`position` 付き)は、持たない要素の上に描かれる。透明度がちょうど1になった瞬間だけ層が消えて、文字が下に隠れ、ちかちかした。
  - **次は**: 手前に出したい文字には `position: relative` を付ける。
- **部品の受け取る値の名前違い**: `@remotion/shapes` の Heart は `size` ではなく `height` で大きさを受け取る。間違えると、エラーなしで何も描かれない。ブラウザのエラー記録(NaN)から見つけた。
- **チュートリアル**: 光らせるボタンは、作るときに登録する。周りを半透明でおおい、光っている所だけ押せるようにする。キーボードの操作も止める。窓が開いている間は引っ込む。途中で閉じても続きから再開できる。

## 8. 動画(PV)

- **動きが10倍速になっていた**: Playwright の時計は、`install()` しただけでは止まらず、流れ続けていた。1コマ撮るのに0.3秒かかるので、そのあいだに時計が進み、動画の中の動きが速くなっていた。2回、別の原因と取り違えて直した(0.55倍に遅くする・描画の合図を置き換える)。
  - **次は**: `install()` のあとに `pause_at()` で止め、1コマぶんずつ `run_for()` で進める。確かめるときは「60コマ撮ったら、時計が何秒進んだか」と「書き出した動画を0.5秒おきに切り出した絵」の両方を見る。
- **Remotion を使うなら**:
  - すべての動きを「何コマ目か」から決める。CSS のアニメーションは使わない。
  - 書き出しは途中から続けられない。接続が切れたら、始めからやり直す。
  - 個人や3人までの会社なら、商用でも無料。
- **スキルが読み込めなかった**: claude.ai で有効にしたプラグインのスキルが、このPCの Claude Code には届かなかった。`npx skills add remotion-dev/skills` で、このPCに入れたら使えるようになった。
  - **次は**: スキルが一覧に出ているかを、作業の最初に確かめる。
- **静止画で確かめるときは、数えて確かめる**: 「題名と札が出ている」ことだけを見て、URLの行が消えているのを見落とした。出ているはずのものを、ひとつずつ確かめる。
- **X 向け**: 音を消して流れることが多いので、文字で伝える。無料のアカウントで最大2分20秒まで。要素を詰め込みすぎると伝わらないので、物語の流れ(始まり → 育てる → 結果)にする。

## 9. 確かめ方(テスト)

- 仕組みの個別テスト(Node なしで動かすため mini-racer)と、偽の DOM で画面を一通り操作するテストを用意した。直すたびに両方を流した。
  - 偽の DOM には `classList` や `querySelectorAll` がない。画面のコードは `className` などの基本だけで書くと、テストで動かしやすい。
- 見た目と操作は、実ブラウザ(Playwright・Chromium)で、PCの幅(1200)とスマホの幅(390)の両方で撮って確かめた。
  - 「押せない」ことの確認は、要素を指定して押すのではなく、画面の位置を押して確かめる。
- この作業環境では、ブラウザに必要な部品(libnss3・libnspr4)が無かった。`apt-get download` して展開し、`LD_LIBRARY_PATH` で渡した。セッションごとに作り直しが要る。
- 音は、私の環境では聞けない。鳴らしたときにエラーが出ないことまでを確かめ、聞こえ方はユーザーに確かめてもらう。

## 10. ユーザーとのやりとり

- 出力は、進捗の連絡も含めてすべて日本語にする。
- すでに済んだ手順の説明を繰り返さない。手順を書く前に、記録で済んでいるかを確かめる。
- 秘密の鍵は、会話に貼らない・貼らせない。`.env` は変数の名前だけを読み、値は読まない。
- 「なぜ速くするの」のように、頼んでいない変更を勝手に入れない。遅くしたい・変えたいと言われたことだけを変える。
